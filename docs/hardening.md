# Как сделать AviaProofAI «железобетонным»: рекомендации

Ниже — разбор по уровням: что **уже реализовано** в коде, и что **рекомендуется**
сделать при внедрении на боевой Teamcenter. Приоритеты: P0 — до запуска,
P1 — первый месяц эксплуатации, P2 — плановое развитие.

## P0. Уже реализовано (проверено тестами)

| Механизм | Где |
|---|---|
| **REST-протокол заказчика** (`RestServices`, `RequestEnvelope`, cookie `ASP.NET_SessionId`, `getItemAndRelatedObjects`) — ровно ваш рабочий PHP-формат | `app/services/teamcenter/rest_client.py`, `mapping.py` |
| **SOAP-протокол** (альтернатива, `TC_PROTOCOL=soap`) | `client.py` |
| Таймауты раздельно: соединение / чтение | `TC_CONNECT_TIMEOUT`, `TC_TIMEOUT` |
| Ретраи сетевых ошибок и HTTP 5xx с backoff (0.5s, 1s); Fault/`<error>` не ретраятся | оба клиента |
| Автоперелогин при истечении сессии (повтор вызова 1 раз) | оба клиента |
| Пагинация `getChildren` (`page_size`/`start_index`) — спецификации на тысячи требований | оба клиента |
| Защита от SSRF: файлы контента только с хоста TC; лимит размера файла | оба клиента |
| Идемпотентная синхронизация, снапшоты истории, изоляция ошибок по записям | `sync.py` |
| Правки не пишутся в TC без двойного разрешения (сервис + пользователь) | `settings_service.py` |
| LLM-фолбэк: внешняя модель недоступна → эвристики, сервис жив | `llm/` |
| 75 e2e-тестов: контракт REST и SOAP, ETL, LLM, API, права | `tests/` |

## P0. Рекомендуется сделать до запуска

1. **Сверить контракт с реальным TC на стенде.** Запустите
   `python -m app.cli sync` против реального `org-tc2` с `TC_PROTOCOL=rest` и
   проверьте лог. Если какой-то элемент ответа отличается от заглушки —
   правится только `mapping.py` (пути `REST_*_PATH`, атрибуты). Шаблон:
   сравните фактический XML ответа с `docs/teamcenter.md`.
2. **Общая сессия с PHP.** Если Koseven уже логинится в TC, передавайте
   значение `ASP.NET_SessionId` в сервис (`TC_SESSION_ID` или заголовок
   `X-TC-Session` на `/sync/run`) — не плодите лишние сессии на сервере TC
   (лимит одновременных сессий в TC ограничен).
3. **Секреты.** `TC_PASSWORD`, `API_KEYS` — не в `.env` в репозитории, а в
   secrets-хранилище (Vault / K8s Secret / переменные окружения CI). Пароли
   нигде не логируются.
4. **TLS.** `TC_VERIFY_SSL=true`, сертификат TC в доверенных. Если TC за
   самоподписанным — добавьте CA в trust store процесса, а не отключайте проверку.
5. **Сетевой контур.** Сервис видит только TC (порт 8080 TC) и Koseven;
   `API_KEYS` меняются по регламенту; `/health` — только внутри контура.

## P1. Первый месяц эксплуатации

6. **Блокировка параллельных синхронизаций.** Сейчас два одновременных
   `/sync/run` могут гонять ETL параллельно. Добавьте advisory-lock по
   `spec_uid` (PostgreSQL `pg_try_advisory_lock`) или флаг в `sync_runs`
   (`status=running` → повторный запуск возвращает 409).
7. **Структурный лог с run_id.** В продакшене полезен JSON-лог: каждая строка
   `{"run_id": N, "op": "getChildren", "node": "rev-...", "ms": 120}`.
   В `sync.py` уже есть `SyncRun` — подключите `logging` c extra-полями и
   собирайте в ELK/Loki.
8. **Alembic-миграции.** Схема сейчас создаётся автоматически; на боевой БД
   подключите Alembic, чтобы менять схему без потери данных.
9. **Метрики.** `/health` дополните `/metrics` (prometheus-client):
   длительность синхронизации, число замечаний по severity, ошибки TC по типу,
   счётчик push-правок. Алёрты: синхронизация failed 2 раза подряд,
   `cert_risk` вырос, запись в TC «тихо» включена.
10. **Бэкап PostgreSQL.** `pg_dump` по расписанию + тестовое восстановление.
    БД — единственное хранилище истории правок (аналитический слой).

## P1. Устойчивость к данным

11. **Пакетная загрузка атрибутов.** Для спецификаций на 10 000+ требований
    `getRequirements` по одному uid — N вызовов. Сгруппируйте по 100–500 uid
    на вызов (операция это позволяет) — минуты вместо часов.
12. **Ограничение глубины и защита от циклов.** `max_depth` уже есть; добавьте
    детекцию цикла по множеству посещённых uid (сейчас цикл упадёт по глубине —
    работает, но шумно в логах).
13. **Retention снапшотов.** История растёт на каждое изменение. Добавьте
    задачу очистки снапшотов старше N месяцев (например, 12 — по регламенту
    сертификации обычно нужен срок хранения, а не бесконечность).
14. **Дедупликация замечаний анализа.** Сейчас при повторном аудите старые
    замечания закрываются — ок; добавьте уникальный ключ
    `(kind, requirement_uid, other_requirement_uid, hash(details))`, чтобы не
    плодить дубли в один прогон.

## P1. LLM-ядро

15. **Circuit breaker для LLM.** При падении внешней модели — не дёргать её
    каждым требованием: после 3 ошибок подряд переключаться на rule-based на
    TTL (например, 5 минут) и поднимать метрику.
16. **Кэш ответов.** Аудит одного и того же текста (hash) — один вызов LLM.
    Это и деньги экономит, и ускоряет повторные прогоны.
17. **Версия промпта в analyses.** Храните `prompt_version` в `details` —
    при изменении промптов можно понять, почему изменились результаты.
18. **Ограничение размера текста на вход LLM.** Требования бывают с
    вложениями; режьте по токенам (например, 3000) с пометкой в details.

## Улучшения для PHP-клиента (Koseven) — по коду заказчика

Разбор присланного кода (login через JsonRestServices + RestServices):

**Что уже хорошо:**
* логин отделён от операций, сессия передаётся параметром — правильная схема
  (не логинить на каждый запрос!);
* конфиг вынесен в Kohana-конфиг, пароль не зашит в код;
* curl-ресурсы закрываются, HTTP-код проверяется.

**Что стоит улучшить (и что уже сделано в Python-сервисе):**

1. **Ручной разбор Set-Cookie → cookie-jar.** `preg_match_all` + `parse_str`
   ломается на нескольких cookie/`expires`/`HttpOnly`. Используйте
   `CURLOPT_COOKIEJAR`/`CURLOPT_COOKIEFILE` (curl сам хранит и шлёт cookie),
   либо готовый парсер. В сервисе cookie ведёт httpx автоматически.
2. **Нет таймаутов и ретраев.** `curl_setopt($ch, CURLOPT_CONNECTTIMEOUT, 10);
   CURLOPT_TIMEOUT, 60`; ретрай транспортных ошибок с паузой. В сервисе —
   `TC_CONNECT_TIMEOUT`/`TC_TIMEOUT`/`TC_RETRIES`.
3. **Нет проверки SSL.** `CURLOPT_SSL_VERIFYPEER, true` (по умолчанию) +
   доверенный CA; не отключать проверку «для удобства». В сервисе —
   `TC_VERIFY_SSL=true`.
4. **Нет обработки ошибок авторизации.** При неверном пароле TC вернёт
   не-200/JSON-error — проверяйте тело ответа и пишите в лог осмысленное
   сообщение, а не «false». В сервисе — `TcAuthError` с текстом сервера.
5. **Срок жизни сессии.** TC-сессии протухают — при HTTP 401/ошибке
   авторизации перелогинивайтесь и повторяйте запрос один раз
   (в сервисе — автоперелогин при истечении сессии).
6. **Опeчатка `descrimator`.** По документации — `discriminator`; работает
   и так (поле пустое), но лучше исправить, чтобы не сбивало с толку.
7. **Двойной слэш в URL.** `$tc_url . '/JsonRestServices/...'` при
   `tc_url` с завершающим `/` даёт `//JsonRestServices`. Большинство серверов
   терпит, но лучше `rtrim($tc_url, '/') . '/JsonRestServices/...'`
   (в XML-функции у вас уже так).
8. **Пароль в логах.** Никогда не логируйте `$login_payload` целиком —
   логируйте только факт входа/ошибки. В сервисе пароли не логируются.
9. **Общая сессия между PHP и Python.** Если PHP уже залогинился — передайте
   `ASP.NET_SessionId` в сервис (`TC_SESSION_ID` / `TC_AUTH=session`), чтобы
   не плодить сессии на TC.
10. **Ограничение попыток входа.** Логин — единственное место, где TC может
    заблокировать учётку; держите частоту попыток низкой (ретраи — только
    транспортные, не на 401/403).

## P2. Плановое развитие

19. **Эмбеддинги вместо TF-IDF.** Для больших спецификаций RAG-скан на TF-IDF
    может пропускать смысловые пересечения. Подключите векторную модель
    (тот же LLM endpoint): интерфейс в `rag.py` уже готов к замене индекса.
20. **Параллельный обход разделов.** Разделы спецификации независимы —
    `ThreadPoolExecutor` по веткам дерева ускорит ETL в разы (осторожно с
    нагрузкой на TC: лимит потоков 4–8).
21. **Webhook-уведомления.** При появлении `critical`-замечания или после push
    правки — POST в корпоративный мессенджер/почту.
22. **Аудит-трейл пользователей.** Таблица `audit_log` (кто, когда, что менял
    в двойнике, кто подтвердил push) — пригодится для сертификации.
23. **Rate limiting API** (slowapi): Koseven и внешние интеграции не должны
    случайно положить сервис.
24. **Проверка «свежести» данных.** Дашборд показывает возраст последней
    синхронизации; добавьте предупреждение, если `last_synced_at` старше
    регламента (например, суток).
